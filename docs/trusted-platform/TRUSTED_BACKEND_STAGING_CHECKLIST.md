# Trusted Farm staging acceptance checklist

This checklist authorizes no deployment, account creation, role grant, credential transmission or infrastructure change. The operator must approve/provision actual targets and access separately. The example JSON contains reserved example hosts/IPs and no credentials; do not deploy it unchanged. It shows a Windows, single-backend-identity DPAPI profile. Multiple backend nodes require the existing reviewed shared certificate/key-ring profile, not node-local DPAPI.

1. Verify the Farm source ZIP hash, source manifest and shared adapter manifest. Keep Revision 5 rollback artifact and database backups. Revision 6 does not add a new database migration over Revision 5.
2. Obtain the separate matching Trusted Platform package. Review its OpenBao and management API/UI guide. The Farm gateway is transport, not a replacement for business authorization.
3. Choose trusted backend host, vault host, public gateway host and exact public origin. Confirm which administrators can inspect each host. Keep vault/bootstrap credentials and backend publish files off the gateway.
4. Operator provisions the least-privilege Farm runtime role for the single typed project path. No root token or unseal key belongs in application configuration. Set reviewed secret values with UTC expiry through the trusted management process. The platform package owns actual management workflow instructions.
5. Provision absolute credential files outside publish/webroot, a protected persistent Data Protection key directory and TLS certificate trust. Windows PC local HTTPS uses reviewed certificate-store selection; IIS uses operator-managed TLS. Do not bypass certificate warnings or enable invalid-certificate acceptance.
6. Configure OpenBao mode, SQL Server provider and exact host/proxy settings. Keep cache/backplane disabled until their separate TLS/ACL endpoints have been reviewed. No environment-wide automatic forwarded-header trust is permitted.
7. Review/apply committed SQL under a separate approved migration identity only if missing. The application never auto-creates/migrates the production database. Use the read-only preflight guide to collect actual SQL/IIS evidence; it does not consume/approve vault configuration for you.
8. Verify startup with authorized vault access succeeds. Verify missing/expired/revoked access fails closed. Record no secret values. Test reviewed runtime version rotation and supervisor restart in isolated staging with reversible synthetic business activity.
9. Verify gateway root-host login, CSRF and backend cookie attributes over actual HTTPS. Confirm private backend and management routes are not publicly reachable. Test permission removal, cross-company/branch requests and existing cookie revocation. One-IP forwarding checks are not a network firewall.
10. Rehearse SQL transaction interruption/rollback, durable messages/outbox restart, Redis cache outage and two-node backplane recovery using disposable staging data. Do not run mutation harnesses against live customer data. Reconcile journals and stock after the exercise.
11. Perform browser/mobile/native-language UAT, realistic dataset/query-plan/load tests, backup/restore, monitoring and certificate/key expiry checks. In-flight calls have an explicit revocation window; document operational cancellation/drain and provider-side revocation.
12. Record customer-approved Bangladesh company policy, payroll/tax settings, opening balances and operational acceptance for all four first-live modules. No statutory suitability or production approval follows from source tests alone.

The included process/HTTP tests run only against disposable local synthetic fixtures. Shared framework/vault tests are separate evidence and are not added to Farm's totals. Customer OpenBao, SQL Server, Windows/IIS and production TLS have not been executed by this source release.
